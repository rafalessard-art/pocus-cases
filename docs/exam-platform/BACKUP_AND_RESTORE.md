# Backup, restore test and account recovery (local, $0)

All backups live in the encrypted image `~/POCUS-Private/POCUS-Backups.sparsebundle` (mounted at
`/Volumes/POCUS-Backups`), outside any synchronised folder. Nothing in this document is a secret;
passwords and keys are typed into hidden prompts and never written to disk.

| Script | What it does |
|---|---|
| `scripts/ops/backup-hosted.sh` | Read-only dump of a hosted project: roles, schema, application data, sign-in and stored-file tables, every stored file, row counts and checksums. |
| `scripts/ops/backup-local.sh` | Git bundles of every branch, untracked and ignored files, de-identified media, private documents. |
| `scripts/ops/restore-test.sh` | Rebuilds a hosted backup in a disposable local stack (localhost only), verifies it, then removes it. |
| `scripts/ops/restore-diagnose.sh` | Content-free summary of a restore log (error classes, table names, line numbers). |

## Restore test

```
hdiutil attach ~/POCUS-Private/POCUS-Backups.sparsebundle
cd ~/pocus-portal && bash scripts/ops/restore-test.sh
```

1. **Isolation, checked before any data is restored.** The disposable stack (project id
   `pocus-restore-test`, ports 55320–55329) runs on a Docker network created with
   `com.docker.network.bridge.host_binding_ipv4=127.0.0.1` and is started with
   `supabase start --network-id`. Studio and the mail catcher are not started. The script then
   checks Docker's published ports, the Mac's listening sockets (`lsof`) and a connection attempt
   through each of the Mac's own network addresses. Any port reachable beyond 127.0.0.1 stops the
   test and removes the empty stack. (The address probe runs from the same Mac; it proves the ports
   are not bound to network interfaces, which is what another device would need.)
2. **Application data**: roles, schema and data in one transaction; every application table's row
   count is compared with the backup manifest.
3. **Stored files**: bucket and object rows restored; every file uploaded and read back with its
   SHA-256 compared with the manifest.
4. **Authentication**: only the tables that identify people are restored (`auth.users`,
   `auth.identities`, `auth.mfa_factors`). Migration history and short-lived tables (sessions,
   refresh tokens, one-time tokens, challenges, flow state, audit log) are skipped on purpose: they
   belong to the running Auth service and collide with a fresh stack; people simply sign in again.
   Then every portal profile is checked: an account with the same id exists, it can sign in (a
   one-time link generated by the admin API, never emailed) and the session resolves to its own
   portal record and role. Admin roles still require the authenticator (aal2); the check does not
   bypass that.
5. **Fallback drill**: the sign-in tables are emptied in the disposable stack and the fallback
   below is performed and verified the same way.
6. **Teardown**: the stack, its data volumes and the restore network are removed and the removal is
   counted (containers, volumes, network all 0). `--keep` leaves it running; `--teardown` removes it later.

The report gives four separate results (application data, stored files, authentication recovery,
fallback drill) and an overall **COMPLETE**, **PARTIAL** or **NOT RESTORABLE AS IS**. A content-free
copy goes to `~/pocus-portal/.wp4/`.

## Account recovery

**Primary** — restore `auth.users`, `auth.identities` and `auth.mfa_factors` from the backup.
Accounts keep their ids, so `public.profiles` (whose id *is* the account id) links up unchanged;
passwords and authenticator apps keep working.

**Fallback** — if those tables cannot be restored (for example after an Auth schema change), for
each portal profile create an Auth account with **the same id and email** (`auth.users` plus an
`email` identity). The profile, its role and every record that references it link up unchanged.
The person then signs in with an emailed code, sets a new password and re-enrols the authenticator
app. On a hosted project, the owner account is recreated first (from the SQL editor), followed by a
password reset and authenticator enrolment before admin MFA is enforced.

Never create a *new* account with a different id for an existing person: their records would stay
attached to the old id.
